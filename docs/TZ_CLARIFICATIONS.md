# Пояснения по спорным пунктам ТЗ

## Есть ли в ТЗ админка?

Да. В ТЗ это раздел **6. Модуль 5: Админ-панель (Settings UI)**. Под админкой здесь подразумевается не отдельный сайт, а Telegram-команды/кнопки для оператора бота: изменить размер тестового ордера, минимальный чистый спред, фильтр ликвидности и включить/поставить мониторинг на паузу.

В мультиюзерном сценарии важно разделять роли:

- **Пользователь**: подписывается на сигналы, открывает 1-click ссылки, подтверждает сделки в своем кошельке.
- **Админ/оператор**: управляет глобальными настройками стратегии. Админ определяется по numeric Telegram user ID из `ADMIN_IDS`, а не по username.

## Как возможна 1-click торговля без хранения приватных ключей?

Бот не подписывает транзакции и не отправляет средства сам. Кнопка в Telegram открывает URL агрегатора, например Jupiter, с заранее заполненной парой, суммой покупки и slippage. После клика пользователь видит подготовленный swap в браузере/кошельке и сам подтверждает транзакцию в Phantom/Solflare.

То есть “1-click” в ТЗ означает быстрый переход к предзаполненной сделке, а не custody-бота с приватными ключами. Полностью автоматическая покупка/продажа без подтверждения пользователя потребовала бы хранить ключи или использовать delegated/session-key механизм, чего в текущем ТЗ явно запрещено.

## По какому алгоритму бот дает сигналы без нейронки?

Нейросеть для такого сигнала не нужна. Сигнал строится детерминированно по рыночным данным:

1. Получить котировки/пулы по Solana DEX из Raydium, Orca, Meteora или агрегированного API.
2. Отфильтровать пары по минимальной ликвидности и 24h volume.
3. Сгруппировать котировки по mint токена.
4. Для каждого токена найти минимальную цену покупки и максимальную цену продажи среди DEX.
5. Посчитать gross spread: `(sell_price - buy_price) / buy_price * 100`.
6. Вычесть расходы: DEX fee на покупку, DEX fee на продажу, slippage и фиксированную Solana priority fee в процентах от размера ордера.
7. Пропустить токен через антискам-фильтр.
8. Отправить сигнал только если net spread выше заданного порога.

Это было описание минимального scaffold. По обновлённому ТЗ такой price-arbitrage scanner недостаточен: сигнал должен подтверждаться executable quote полного маршрута `USDC → TOKEN → USDC`, а не только сравнением цен.

## Как проходит антискам-проверка?

Антискам-проверка должна выполняться до отправки сигнала. Минимальный набор критериев из ТЗ:

- mint authority revoked;
- freeze authority revoked;
- LP burned/locked минимум на 80%;
- top-10 holders владеют не более 30% supply, исключая DEX-пулы и burn-адреса.

Если хотя бы один критерий не пройден, сигнал не отправляется. Текущий код содержит RugCheck-compatible клиент и единый `SecurityReport`; для production-интеграции нужно адаптировать маппинг под фактический JSON выбранного провайдера: RugCheck, GoPlus или Helius Metadata.

## Как продавать токен по сигналу?

Для настоящего арбитража SELL — не дополнительная кнопка после покупки, а вторая половина той же возможности. Без хранения ключей бот может подготовить non-custodial маршрут или транзакцию для подтверждения в кошельке, но не должен публиковать opportunity без подтверждённого SELL route.

Практический UX:

1. Пользователь нажимает “Купить на $25 (Jupiter)” и подтверждает покупку USDC → TOKEN.
2. После исполнения пользователь нажимает “Продать TOKEN (Jupiter)” и вручную выбирает доступный баланс или сумму в интерфейсе Jupiter.
3. Если нужна полностью автоматическая вторая нога сделки, это уже другой режим: custodial wallet, delegated signing или отдельная trading-backend архитектура с явным согласием пользователя и изменением ТЗ.
